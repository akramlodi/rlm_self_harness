# MRCRv2 DeepSeek Smoke Run

## Executive Summary

This directory contains a one-round MRCRv2 smoke experiment using Azure Foundry with `DeepSeek-V4-Flash`.

The round completed successfully and promoted one candidate harness. The candidate improved the observed validation result from **5/6 (83.3%)** to **6/6 (100%)** while increasing validation cost by about **3.4%**. The result is promising, but the sample is very small: only three held-in and three held-out instances, one repetition, and no long-split evaluation.

- Round: 1 of 1
- Environment: synthetic MRCRv2 short split
- Model: `DeepSeek-V4-Flash`
- Configured smoke loop: `m=1`, `v=1`, `k=2`, `t=1`
- Candidate proposals: 1
- Candidates promoted: 1
- Total recorded cost: **$0.05171864**
- Total recorded usage: **240,731 input tokens**, **11,725 output tokens**
- Stop reason: `max_rounds`
- Final harness: `cc1b47c5b1beaadc62d0e450923ecead8dfc431118350b9dd1e3a8034a3d52f2`

## What Ran

The experiment used the MRCRv2 generator in `shrlm/environments/mrcrv2.py`, not an external MRCR dataset. The smoke profile generated a short pool and partitioned it into:

- Held-in: 3 instances, used for mining and validation
- Held-out: 3 instances, used for validation only
- Long test split: generated by the experiment infrastructure but not evaluated in this round

The configured MRCRv2 short shape is approximately 65,536 target tokens with 2 needles. This smoke run does **not** establish performance at the configured 2,000,000-token, 8-needle long shape.

## Accuracy and Validation

Each validation subject ran once over 3 held-in and 3 held-out instances.

| Subject | Held-in | Held-out | Overall | Cost |
|---|---:|---:|---:|---:|
| Baseline | 3/3 (100%) | 2/3 (66.7%) | 5/6 (83.3%) | $0.01694039 |
| Candidate `r01-c01-s4` | 3/3 (100%) | 3/3 (100%) | 6/6 (100%) | $0.01751338 |

The candidate therefore fixed the one observed held-out miss and did not regress on held-in examples.

Important qualification: this is a six-example smoke comparison, not a statistically reliable estimate of general MRCRv2 accuracy. The apparent one-example improvement could be sample-specific and needs confirmation on a larger short pool and then on the frozen long split.

### Baseline failure

The baseline's failed run was held-out instance `mrcrv2-2n-90f94733a86bf4fb__a01`.

- Outcome: resource termination, not a normal verifier wrong-value failure
- Error: `TimeoutExceededError: Timeout exceeded after iteration 4: 300.6s of 300.0s limit`
- Usage before termination: 4 model calls, 9,852 input tokens, 322 output tokens, `$0.00203610`
- Mining diagnosis: the root spent seven iterations analyzing the conversation's vocabulary and structure but did not extract the requested answer before resources ran out
- Failing level: `no_recursion`
- Agent mechanism: `premature_termination`
- Verifier cause: `resource_terminated`

The validation JSONL represents this as `passed: false`; the detailed run artifact carries the timeout and execution trace.

## The Proposal

There was exactly **one** proposal. It materialized successfully; there were no materialization failures and no skipped patterns.

Proposal ID: `r01-c01-s4`

- Surface changed: `S4_verification_instruction`
- Base harness: `be733515a34beefc2b17e74111e40b19fad5b132fd8ed1b149e8b2f11283210d`
- Candidate harness: `cc1b47c5b1beaadc62d0e450923ecead8dfc431118350b9dd1e3a8034a3d52f2`
- Predicted effect: prevent premature termination by requiring the model to check for unvisited slices before finalizing

The added instruction was:

> Before setting `answer["ready"] = True`, verify that every slice of the input has been visited. If any slice remains unvisited, do not mark the answer as ready; instead, continue decomposing.

The proposal explicitly identified two risks:

1. The model could loop indefinitely if it cannot determine slice boundaries correctly.
2. The model could delay answer submission on tasks where full visitation is unnecessary.

In this smoke round, neither risk produced an observed failure. However, the candidate still made no sub-calls: `mean_sub_calls = 0.0` for both baseline and candidate. Therefore this proposal was tested only in the no-recursion path; the smoke run does not demonstrate its effect on recursive decomposition.

## Mining Findings

Mining processed 3 held-in instances:

- 2 mining runs passed
- 1 mining run failed
- The mined failure was the same pattern later addressed by the proposal: the root analyzed structure but did not produce the requested answer before the resource limit
- The attribution stage classified the failure as causal and associated it with `S4` / premature termination / no recursion / resource termination

The attribution and proposal stages then produced one actionable S4 edit. No S1-S3, S5-S10 edits were proposed in this round.

## Problems and Open Issues

1. **Very small evaluation sample.** Six validation runs are insufficient to estimate general accuracy.
2. **No long-context result.** The 2M-token, 8-needle split was not evaluated.
3. **No recursion coverage.** Both baseline and candidate had zero sub-calls, so the sub-verifier was unavailable and the effect of the harness on recursive behavior remains untested.
4. **The observed problem was resource termination.** The baseline did not fail because the answer was semantically wrong; it timed out after spending iterations on analysis without extracting the needle.
5. **Candidate cost increased slightly.** Validation cost rose 3.38%, likely reflecting additional verification behavior, though the smoke sample is too small to attribute this confidently.
6. **The candidate may encourage over-checking.** The proposal's own stated risk is delayed or never-ending answer submission when full slice visitation is unnecessary.
7. **Configured versus measured context.** The generator targets the short MRCRv2 shape using a character proxy; reported API token counts are model usage for actual requests and should not be read as proof that the full 2M long split was exercised.

## Recommended Next Check

Run the promoted harness against a larger short validation set, keeping the same DeepSeek pricing/configuration, and compare against the baseline on enough instances to determine whether the held-out improvement repeats. Then run the frozen promoted harness on the long test split separately; do not treat this smoke result as a 2M-token evaluation.
